# Decisions

This file records each design decision and its reason. The newest decisions are at the end.

| # | Decision | Reason |
|---|----------|--------|
| D1 | Product name: **Apsis**. | The name is short. An apsis is the nearest or the farthest point of an orbit. Persons that know orbits know this term. |
| D2 | Project directory: `~/Desktop/test/apsis`. All tools, caches and downloads stay in it. | Instruction of the owner (2026-10-13): do the work in a new directory below `test/`. |
| D3 | Software: TypeScript, Vite, React, three.js, zustand, vitest. The tests of the screens use playwright-core and the Chrome browser that is on the computer. | The output is static, with no server. No browser download is necessary. |
| D4 | Planet ephemeris: JPL DE440 (`de440s.bsp`), as a new fit with Chebyshev polynomials for 1949-12-14 to 2100-01-12 TDB, 4.3 MB. Fit tolerance 10 m. | DE440 is the usual reference for planet ephemerides. The full file (32 MB) is too large for a web page. The product publishes the measured fit error. |
| D5 | Reference data: JPL Horizons API (planets, spacecraft, moons, small bodies). The directory `truth/horizons/raw/` has the text that the API sent, with no change. | In the specification, the reference values must come from Horizons, from analytic solutions or from published documents of the missions. The text with no change is the record of the source. |
| D6 | Internal time: TDB seconds after J2000. Internal frame: ICRF, origin at the solar system barycenter. Units: km, km/s, s. | SPICE and DE440 use the same time, the same frame and the same units. Conversions occur only at the user interface. |
| D7 | Physical constants (GM, radii, rotation) come from the NAIF files `gm_de440.tpc`, `pck00011.tpc` and `naif0012.tls`. A script converts these files. | No constant comes from memory. |
| D8 | Moons use an analytic model (an ellipse with constant rates of the node and of the periapsis) that is a fit to Horizons data. Small bodies use Chebyshev fits of Horizons vectors (1980 to 2060). The product publishes the measured errors. | Full satellite ephemerides are too large. The user must know that the moon model is approximate. |
| D9 | One mission model for the two modes. A mission has a *plan* (patched conics: Lambert legs and flybys) and a *flight* (numerical trajectory with maneuvers in the full force model). | In the specification, the two modes must have the same engine and the same state. |
| D10 | Integrator: Runge-Kutta-Fehlberg 7(8) with a variable step. | The order is high, and the integrator uses no library. The tests compare the order and the accuracy with the analytic two-body solution. |
| D11 | File formats that the application writes or reads: CCSDS OEM and OPM (KVN), GMAT script, STK ephemeris (`.e`), and the Apsis mission file (JSON). | OEM and OPM are the standards that STK, GMAT, Orekit and other programs read. |
| D12 | All text is in `src/i18n/locales/en.json`. A new language is a new JSON file in the same directory. The application shows the language control automatically when there is more than one file. | In the specification, it must be possible to add Japanese with no change to the code. |
| D13 | Planet and moon maps come from open sources only. `docs/ASSETS.md` gives each asset, its source and its license. (D27 and D28 changed this decision.) | Specification: each asset must have a known license. |
| D14 | Test limits are regression limits. The product publishes the *measured* value of each check, not the limit. First test results (2026-10-14): the author corrected three limits and wrote the reason for each correction in the test file. These limits were estimates that the author made before the first measured values. The three limits: accuracy of the TDB-TT formula (30 microseconds), planet centers of Uranus and Neptune, moon model of Mimas. For these planet centers, two JPL sources do not agree: the difference is some thousand km. The author changed no engine constant to get a test result in its limit. | In the specification, the adjustment of a test to prevent a failure is not permitted. A limit must have a physical reason. |
| D15 | The force model includes the point masses of Ceres, Vesta and Psyche (1980 to 2060, the range of the small-body data). | First result of the asteroid propagation test: Vesta had an error of 1.15 km in 168 days. The cause is the gravity of Ceres (with Ceres in the model the error is 0.01 km). The correction is in the model, not in the test limit. |
| D16 | Limit of the patched-conic flyby check: the difference between the speeds at infinity before and after a flyby is not more than 3 %. | The first limit (100 m/s) was an estimate with no data. Cassini at the Earth has 155 m/s, which is approximately 1 % of 16 km/s. The limit of 3 % is a regression limit (D14): the project has no document that gives the accuracy of this model. The largest measured value is 1.7 % (Cassini at Jupiter). The numerical model then makes each flyby a flyby with no burn. |
| D17 | The application makes the actual missions again from the sequence of bodies and the actual dates only. The engine calculates the path when the application operates. | In the specification, trajectories from an earlier calculation are not permitted. The dates are actual data (JPL Horizons and NASA pages). The path is a result. |
| D18 | Conversion of a plan to a flight (`refinePlan`) has three stages. Stage A finds one control (launch velocity, correction maneuver or deep-space maneuver) that gives the aim point and the periapsis time of the next body. The engine measures the aim point on the approach hyperbola, approximately 30 body radii before the periapsis. Stage B makes each flyby a flyby with no burn. It changes the control before the flyby and the arrival velocity at the next body to make the correction after the flyby a minimum (Gauss-Newton method with equality constraints and a constant arrival time). Stage C (legs with a deep-space maneuver) moves the aim point of the flyby before the maneuver with the Nelder-Mead method. | The osculating hyperbola at the periapsis of a planet with an equatorial bulge is not the approach asymptote (Jupiter: 2 % in the speed at infinity). The dates of a good plan are near the minimum of the energy, where the speed does not change with the date: with the arrival time as a variable, the matrix of the derivatives is singular. |
| D19 | A plan can correct the flyby times for the time that the spacecraft is in the sphere of influence (`soiTime`). | The patched-conic model with a sphere of influence of zero size puts the flyby at an incorrect time. For Jupiter, the error is some hours. The correction gives a better first estimate to the numerical solver. |
| D20 | An encounter report has two speeds at infinity: `vinf` (approach hyperbola) and `vinfClosest` (two-body orbit of the state at the closest approach, GM of the planet system). | The reference values from JPL Horizons use the second definition. A comparison must use the same definition (Pioneer 11 at Jupiter: 2 % difference between the two). |
| D21 | Actual missions from their dates: limit of the periapsis radius of a flyby 3 %, speed at infinity 1 %, sum of the correction maneuvers 200 m/s. | The application knows only the dates. The actual flights used maneuvers that it does not know: the sum of the velocity jumps in the JPL Horizons trajectory of Cassini between Venus 2 and the Earth is 97 m/s (`tests/famous.test.ts` measures this value). |
| D22 | The end of each integrator step is at a time that a 64-bit number can hold. The integrator gives each stage time to the force model in two parts: the start of the step and the time after that start. It uses compensated sums for the state. The ephemeris reader accepts the time in two parts. Default relative tolerance 1e-13. | Measured result (2026-10-14): the end position of a flight of 0.8 years from a parking orbit had a noise of approximately 1 km. The cause was the precision of the time (1.2e-7 s near 2030 = 2 mm of motion for each step, which the departure from the Earth multiplies by 7e4), not the tolerance. After the change the noise is 0.003 km, and 352 of 352 default missions have a solution (before: 334). |
| D23 | A maneuver that a solver calculated has an `anchor`: the state immediately after the impulse. The propagation continues from the anchor if the state of the propagation is nearer to it than 1 km and 1 mm/s. The difference is in the maneuver event. | A path with three flybys multiplies a difference in the last bit of a number to some thousand kilometers. JavaScript engines do not give the same last bit for all functions. With anchors, a saved mission gives the same trajectory in all browsers. Each arc is an integration of the engine, as before. A change of a maneuver must remove the anchors after it. |
| D24 | Quick mission (Explorer mode): the user gives a target, a goal (flyby, orbit, rendezvous, entry) and a type of flight (`efficient` or `fast`). The engine searches launch dates for one synodic period (1.1 to 3 years) and flight times from 0.35 to 1.7 Hohmann times (not more than 16 years). The search uses a 96 x 120 grid, then a grid with smaller steps. `efficient` = minimum velocity change. `fast` = shortest flight for not more than 1.0 km/s (flyby, entry) or 1.5 km/s (orbit, rendezvous) above the minimum. Default altitudes are in `QUICK_ALTITUDE`. The orbit at Pluto is nearer to Pluto than the orbit of Charon. | One minute from the first screen to a flight. The same solver and force model as the Expert mode. An orbit that goes across the orbit of Charon is chaotic. |
| D25 | The arrival burn is one impulse at the periapsis. The engine finds the size for which the first apoapsis of the propagated orbit has the radius of the plan. Published values of actual insertion burns (Cassini, Juno) are not reference values. | Actual insertion burns are long (Cassini: 96 minutes): the published velocity change includes gravity losses and is not the impulsive value. The comparison is in the list of items with no check. |
| D26 | The engine has no text for the user. Errors are codes (`QuickError.code`, `Trajectory.failure.reason`, `IoError.code`). The user interface converts the codes to text. | All text must be in the locale files (D12). |
| D27 | The spacecraft are models of this project that the code makes (nine models in `src/render/spacecraft`). They have no logo, no flag and no text. The most important dimensions agree with published documents where `docs/ASSETS.md` gives the document. | There is no license problem and no download, and the models are small. This project does not accept a box with panels. |
| D28 | Body maps are actual mission data only. Each map has a license statement in the words of its source. The project uses no files from Solar System Scope. Shader code makes the pictures of the Sun, of the cloud top of Venus and of bodies with no map. The product tells the user that these pictures are not images from a camera. | The first texture set had nine files from Solar System Scope (CC BY 4.0). They are assets of a different application, and they contain areas that are not actual data. In the specification, a copy of the assets of other software is not permitted, and each picture must agree with the actual body. |
| D29 | `tests/quick.test.ts` (352 default missions) and the last-encounter checks are tests of the solvers: the target is an input. They do not show that the physical model is correct. | In the specification, a test that uses the output of the code as a reference value is not permitted. The names of these tests show that they are solver tests, and the report of the accuracy checks keeps them in a separate group (`solver`). |
| D30 | A Web Worker (`src/app/worker.ts`) does all long calculations. If the browser cannot start a Web Worker, the same code does the calculations on the page. | The user interface must not stop during a calculation of 10 seconds. For this, the usual headers of a static web server are sufficient. |
| D31 | Each number on a screen has a record of its source and accuracy: a `kind` that gives the method, the limit and the results of the automatic tests (`src/app/provenance.ts`). The tests write each measured value to `src/validation/measured/*.json`, and the Accuracy screen shows these files. | In the specification, the product must let the user see the accuracy limit and the source of each number. A manual copy of a value in the text becomes incorrect when the code changes. |
| D32 | The text of each language is a directory (`src/i18n/locales/en/`) with some JSON files. The application makes one set of texts from these files. (This replaces the one file of D12.) | One file of 100 kB is not easy to change and to keep correct. A new language is a new directory, and no change to the code is necessary, as before. |
| D33 | A trajectory table that the application writes has the steps of the integrator as its samples (default). Before it writes a file, the application measures the interpolation error of the table with the interpolation of the target program and shows it. The STK file tells STK to use Hermite interpolation with 4 points, the same as the check. Limits: 100 000 samples in a written file, 64 MB for a file that the application reads. | Measured results: a table of Voyager 2 with a fixed step of 1 day has an interpolation error of 149 038 km at Neptune. The table with 1569 integrator steps has 0.058 km. A fixed step is the usual default of other programs, and a user of these programs cannot see its error. |
| D34 | Closest approaches of a table from a file: the application finds each interval in which the range rate to a body goes from negative to positive. It then propagates the sample at the start of the interval to the sample at its end. It shows the distance between the end of this propagation and the sample of the file (`missKm`) and gives a warning above 1000 km. | A minimum of the sample distances does not find a flyby between two samples. Measured results for a table of Cassini that has one sample each 10 days relative to the Sun: the application finds all four flybys before Saturn. The three low flybys agree with the 1-minute data to 3.71 km and 0.16 s. A large `missKm` shows a maneuver in the interval (Saturn orbit insertion: 144 327 km). |
| D35 | A flight that the application makes from a table has one start state (a sample of the table) and the maneuvers that the user selects. The engine propagates the path: the path is not a copy of the table. The difference between the flight and the table is a graph. At the start, the selection does not include the maneuvers that the search finds in an interval with a flyby. | In the specification, a path that is not a result of the engine is not permitted. The user sees how far a flight with only these maneuvers is from the file, and can use the targeter to remove the difference. A small error gives a large change of a maneuver estimate in a flyby interval. |
| D36 | For a JPL Horizons table of a spacecraft relative to the solar system barycenter, the Files screen shows a caution. | Measured results: these tables do not agree with the tables relative to a planet. The differences are 118 km (Cassini, 1999) and 117 km (Juno, 2013). The altitude of the Earth flyby of Cassini from the barycenter table is 86 km too small. There is no check of the cause. |
| D37 | A GMAT script that the application writes has the list of the differences between the two force models as comments. The Files screen tells the user that no test opened the files in GMAT or in STK. | GMAT and STK are not available in this work. A file can obey the format of a different program with no test in that program. The product must then tell this to the user. |
| D38 | The comparison flights of the Propagation screen (with one force less or one force more in the model) start again at each maneuver from the state of the flight on the screen (default). An option gives one start only. | With one start, each flyby multiplies a small difference. The values after two flybys then show only that small differences become large in this flight. With a start at each maneuver, a value shows the effect of the force in one arc. |
| D39 | The maps of Deimos, Miranda, Ariel, Umbriel, Titania and Oberon are the Caltech/JPL/USGS maps from Viking and Voyager images (public domain, from NASA 3D Resources and Wikimedia Commons). The areas of these maps with no image data stay as they are: the 3D view shows them in one dark gray color, and the product tells this to the user. | These maps are government data products, not the assets of a product of a company. USGS Astrogeology has no other image map of these bodies. This project does not accept a sphere with one color, and a surface that does not come from data is incorrect. |
| D40 | Saturn, Uranus and Neptune use the global maps of the Hubble OPAL program (CC BY 4.0). For the latitudes that the telescope cannot see, the texture script uses the mean color of the nearest rows, and the asset list shows where. | No spacecraft made a global color map of these planets with a clear license. The rows with a mean color are a small part of each map, and the asset list shows them. |
| D41 | The 3D view has one scale for all sizes and all distances ("True scale"). A symbol, a name and a line have a constant size on the screen. The two modes use the same code for the 3D view (`src/render/scene`). | The specification gives this rule: the product must show each change of a size or a distance to the user. With one scale, there is no change to show. A constant symbol shows the position of a body that is too small for one pixel. |
| D42 | The origin of the 3D view is the object that the camera points to. The setting `logarithmicDepthBuffer` of the 3D library is on. The axes of the 3D view are those of ECLIPJ2000, and the unit is 1 km. | The numbers near the camera are small. Thus 32-bit numbers are sufficient from 1 m to 100 au. |
| D43 | The 3D view shows the flight path relative to the solar system barycenter. Near a body, it shows the part of the path near that body relative to the body. The note line of the view gives the frame of the path. | Relative to the barycenter, a flyby is only a small change of direction. Relative to the planet, the user sees the hyperbola or the orbit. The specification gives this rule: the product must always show the frame. |
| D44 | For each frame, the 3D view calculates the part of the flight path near the spacecraft again from states of the trajectory. It does the same for the orbit line of a body that is larger than a point on the screen. | A line with constant points does not go through the spacecraft when the camera is near. All points of the line are results of the engine. |
| D45 | The automatic camera has three views. In the cruise, it shows the solar system. Near a body, it stays near the spacecraft and keeps the body in the picture. Above the night side of a near body, it shows the body and the path from the side. Then more than half of the body on the screen is in sunlight. Each change has two limits (one to start, one to stop). A camera motion of the user sets the automatic camera to off. | A user with no instruction must see a good picture in one minute. Each limit is an angle: the size of a body from the camera, or an angle between two bodies. Thus the views agree with the shape of each flight. Two limits prevent a change of the view at each frame. |
| D46 | With the automatic time rate, the distance to the surface of the nearest body changes by a constant ratio in a constant display time. This time is 2.2 s to 6 s. The lowest rate is 120 s for each second. At the highest rate, the full flight shows in 22 s. The rate goes to its target with a time constant of 0.13 s. The control always shows the rate, and the user can select a constant rate. | The duration of a flyby is some hours and the duration of a cruise is some years. One constant rate cannot show the two. The time constant does not change with the frame rate of the computer. |
| D47 | The time of the view is one value for the 3D view and for all numbers on the screen (`src/app/clock.ts`). A long frame moves the time by not more than 0.1 s of display time. The time stops at the end of the flight. | The picture and the numbers must agree. When the user cannot see the browser tab, the frames stop. This must not cause a large step of the time. |
| D48 | Explorer mode: the start screen is the 3D view of the solar system at the date of the computer. The user selects a destination and uses one button. The default goal is a flyby and the default type of flight is the one with the small launch energy. Other goals and types are in a closed part of the screen. A second tab has eight actual missions. | The specification gives one minute from the start to a flight, with no instruction. The engine finds the launch date and calculates the flight (D24). Thus the user can make a flight with no instruction about orbits. |
| D49 | The flight screen of the Explorer mode shows the speed and the altitude above the nearest body. It also shows the distances from the Earth and from the Sun, and the next event. The button "Show the numbers" opens the same mission in the Expert mode. A change of the mode keeps the mission, the time of the view and the state of the clock. | The specification gives two rules. The two modes use the same numbers. The user can examine in the Expert mode the items that the Explorer mode shows. |
| D50 | Each body in the 3D view has a record of the source of its picture: a map of mission data, a calculation, or the two. The note button of the view shows this record and the notes of the body, with a link to the list of the maps. | The user must know which part of a picture is data. If a picture comes from a calculation and not from data, the note tells this to the user. |
| D51 | The night side of a body gets light with 0.08 of the brightness of the sunlight. This light is not physical. The notes of the view and the About screen tell this to the user. The Expert mode has a control that sets the light to off. | Without this light, the night side is black. Then the user cannot see the body when the spacecraft is above its night side. With this value, the user can see the night side, but it is much darker than the day side. |
| D52 | The sunlight in the 3D view has the same brightness at all distances from the Sun. The notes of the view and the About screen tell this to the user. | With the actual brightness, Neptune is approximately 900 times darker than the Earth. A screen cannot show this range. |
| D53 | A small body with no radius in the JPL Small-Body Database has a radius of 10 km in the picture. For a body of this type, the flight screen shows the distance from the center and not an altitude. The picture note gives the reason. | The application must not show an altitude that comes from a value with no source. |
| D54 | The notes of the 3D view tell the user that a flight path can show an angle in a view from near the spacecraft. | The picture of a curve has an angle at the point where the curve and the line from the camera have the same direction. This is an effect of the perspective. Without the note, the user cannot know that the angle is not an error of the path. |
| D55 | The About screen has seven parts: user data, rules of the 3D view, engine data, maps, spacecraft models, libraries and names. The list of the maps comes from `public/textures/manifest.json`. The command `npm run build` reads the list of the libraries from their package files and writes their license texts to `licenses.txt`. | A record of the source and the license of each map and each library is necessary. The application must also tell the user that it does not record their operations. Lists that a command makes from the files cannot become incorrect after a change. |
| D56 | The reference text of each measured value is in its test file. A language can replace it with a text for the key `validation.truth.<id>`. A language can also replace the text of the changes of a map (`about.maps.changeText.<id>`). | A second language must be possible with no change to the code. The test file stays the one source of the English text. |
| D57 | The name of an actual spacecraft on the screen comes from the locale files (`spacecraft.<id>`). The table of the engine has the English name for files and as a default. | A second language can give a different form of each name with no change to the code. |
| D58 | The check of the English texts is a script with a closed word list (`tools/ste`). The full check reads all locale files, the files of measured values, the changes of the maps in `public/textures/manifest.json`, `README.md` and the documents in `docs/`. It does not examine the table columns that contain only names and credit lines from sources (`nameColumns` in `tools/ste/technical-names.json`), but it counts their cells. The official dictionary of ASD-STE100 was not available. In the word list, the symbol `?` shows each word for which the project found no source. | A check that a tool can do again gives the same result each time. The record (`docs/STE_CHECK.md`) gives the items that the check can show and the items that it cannot show. |
| D59 | The automatic tests include checks of the texts (`tests/i18n.test.ts`). Each key that the code uses has a text. The screen files contain no words. Each value of a list of the engine has a text. | The specification does not let the code contain text. If a text is not in the locale files, the screen shows its key. |
| D60 | The command `npm run report` writes `docs/VALIDATION.md` from the measured values and from the texts of the Accuracy screen. | A document that a person writes from the numbers can contain an old number. The document and the Accuracy screen have one source. |
| D61 | The time line of a flight has a symbol for each maneuver and each closest approach. The two buttons at the sides of the start button go to the event before and to the next event. In the Expert mode, the size of the 3D view changes with the size of the window. Thus the user sees the view and its time controls at the same time. | The important events of a flight are short. In the two modes, the user must find each event with one click. |
| D62 | A phone that the user holds with the long side down has a screen that is wide and not high. For this screen, the Explorer mode puts its panels in different positions. The start screen shows the destination panel and the list of bodies in one row. The flight screen closes the flight data until the user opens them. | The screen of a phone in this position is approximately 390 points high. With the usual positions of the panels, the launch button was below the edge of the screen. |
| D63 | The 3D view shows its open notes on a part of the other panels. The notes do not move a panel. | The open notes moved the flight data above the top of the screen. This problem occurred on a computer screen also. |
| D64 | The 3D view does not show the name of a body when the spacecraft model is between the camera and the body. | The name of a far body showed on the model. It was not possible to read the name, and the picture was incorrect. |
| D65 | Very near a body, the body is larger than the view. The automatic camera then turns to the side, and the edge of the body stays in the view. The camera is on the side of the Sun. If the part of the body in the view is then dark, the camera goes to the other side of the spacecraft. It then shows the edge of the body that is in sunlight. Each change has two limits. | At the closest approach of the default flight to Mars (altitude 500 km), the view showed only an area of the surface. It was not possible to see that the area was a planet. The edge of the planet, the stars and the spacecraft in one picture show the flyby. |
| D66 | After the last body of a flight, the body button of the flight screen shows the last body that is not a moon. | At the end of the New Horizons flight, the button showed Charon, because the closest approach to Charon is the last event. The destination of that flight is Pluto. |
| D67 | The tool that makes the pictures of the screens (`tools/shots`) does checks for each picture. It records each error and each warning of the browser console. It records each request with no result and each request to a different server. It also records a page that is wider than the screen and a text key on the screen. The tool makes the pictures at three sizes: a computer screen, a phone screen, and a phone screen with the long side down. A person must examine the pictures. | The specification gives this rule: the screens must have no display problem and no console error at the two sizes. A tool finds the problems that a person does not see in a picture. The tool cannot find a problem of the positions of the panels or of the 3D view. |
| D68 | The comparison with other tools (`docs/COMPARISON.md`) gives a label to each statement about a different tool. The label "Page" with a number gives the web page that contains the statement. The label "No check" shows a statement with no source. The project did not operate the other tools. | The specification gives this rule: the project must not write that an item is correct if the project did not examine it. A reader must know which statements come from a source. |
| D69 | The event buttons go to the event before and to the next event. They do not stop at an event that is less than 1 s from the time of the view. While the time moves, the button for the event before uses a larger limit: 1.2 s of display time. | The limit was a part of the flight time. With that limit, the buttons did not stop at one of two events that are near each other. While the time moves, a second use of the button must go to the event before that event. |
| D70 | The tool that makes the pictures of the screens writes a long page as a sequence of pictures. Each picture shows the part of the page that goes into one screen. | The browser cannot make one picture that is higher than 16 384 pixels. In a picture of that type, the lower part showed the top of the page again. The picture then showed a problem that the page did not have. |
| D71 | In the 3D view, a name is on the right side of its symbol. If the name does not go into the view there, it is on the left side. The name of an event is above its symbol. | The name of an event went out of the view at the edge, and the user saw only a part of the name. The flight path goes through the symbol of an event, and the name was on the path. |
| D72 | On a narrow screen, a table that is wider than its panel moves in the panel from side to side. A column of text keeps a size that is sufficient to read it. Two date fields are one below the other. The time control has two rows. | On a phone screen, six tables went out of their panels, and a date field did not show all of its time. The automatic check for a page that is wider than the screen did not find these problems. The page did not become wider. |
| D73 | A graph shows the label of a ring or of a line only if all of the label is in the graph. The top view of a flight does not show a distance ring that is smaller than the center body. In the Tisserand graph, the symbol of an open orbit is at the top of the graph. | At the edge of a graph, a label showed only a part of its text. A person can read a text of this type incorrectly ("2.5 a" for "2.5 au"). |
| D74 | The 3D view shows no name below a panel that is above the view. If the name of an event cannot be above its symbol, it is below the symbol. | A part of a name was below a panel, and the user saw a name with no end. At the right edge of the view, the names of two events were at the same position, and one of them did not show. |
| D75 | A graph does not show the label of a distance ring where the label of a point is.
