# Decisions

This file records each design decision and its reason. Newest entries are at the end.

| # | Decision | Reason |
|---|----------|--------|
| D1 | Product name: **Apsis**. | Short. An apsis is the nearest or the farthest point of an orbit: a term that experts know and that is easy to say. |
| D2 | Project directory: `~/Desktop/test/apsis`. All tools, caches and downloads stay in it. | Instruction of the owner (2026-10-13): work in a new directory below `test/`. |
| D3 | Stack: TypeScript, Vite, React, three.js, zustand, vitest. Screens are tested with playwright-core and the installed Chrome. | Static output, no server. No browser download is necessary. |
| D4 | Planet ephemeris: JPL DE440 (`de440s.bsp`), fitted again with Chebyshev polynomials for 1949-12-14 to 2100-01-12 TDB, 4.3 MB. Fit tolerance 10 m. | DE440 is the reference of the industry. The full file (32 MB) is too large for a web page. The fit error is measured and published in the product. |
| D5 | Truth data: JPL Horizons API (planets, spacecraft, moons, small bodies). The raw responses are kept in `truth/horizons/raw/`. | The specification requires truth from Horizons, analytic solutions or primary documents. The raw text is the record of the source. |
| D6 | Internal time: TDB seconds after J2000.0. Internal frame: ICRF, origin at the solar system barycentre. Units: km, km/s, s. | Same conventions as SPICE and DE440. Conversions occur only at the user interface. |
| D7 | Physical constants (GM, radii, rotation) come from the NAIF kernels `gm_de440.tpc`, `pck00011.tpc`, `naif0012.tls`, converted by a script. | No constant comes from memory. |
| D8 | Moons use an analytic model (precessing ellipse) fitted to Horizons data. Small bodies use Chebyshev fits of Horizons vectors (1980 to 2060). The measured errors are published. | Full satellite ephemerides are too large. The user must know that the moon model is approximate. |
| D9 | One mission model for the two modes. A mission has a *plan* (patched conics: Lambert legs and flybys) and a *flight* (numerical trajectory with maneuvers in the full force model). | The specification requires the same engine and the same state in the two modes. |
| D10 | Integrator: Runge-Kutta-Fehlberg 7(8) with adaptive step. | High order, no external dependency. The order and the accuracy are tested against the analytic two-body solution. |
| D11 | Interchange formats: CCSDS OEM and OPM (KVN), GMAT script, STK ephemeris (`.e`), and the Apsis mission file (JSON). | OEM and OPM are the standards that STK, GMAT, Orekit and others read. |
| D12 | All text is in `src/i18n/locales/en.json`. A new language is a new JSON file in the same directory; the language switch shows automatically when more than one file exists. | The specification requires that Japanese can be added with no change to the code. |
| D13 | Planet and moon maps come from open sources only. `docs/ASSETS.md` lists each asset, its source and its licence. (Changed by D27 and D28.) | Specification: no asset with an unknown licence. |
| D14 | Test limits are regression limits. The product publishes the *measured* value of each check, not the limit. First run 2026-10-14: three limits that I had guessed before the first measurement were corrected with a written reason in the test file (TDB-TT formula accuracy 30 microseconds; planet centres of Uranus and Neptune where two JPL sources disagree by thousands of km; moon model of Mimas). No engine constant was changed to pass a test. | The specification forbids tests that are tuned to pass. A limit must have a physical reason. |
| D15 | The force model includes the point masses of Ceres, Vesta and Psyche (1980 to 2060, the range of the small-body data). | First run of the asteroid propagation test: Vesta had an error of 1.15 km in 168 days. The cause is the gravity of Ceres (with Ceres in the model the error is 0.01 km). The fix is in the model, not in the test limit. |
| D16 | Limit of the patched-conic flyby check: the speeds at infinity before and after a flyby agree within 3 %. | The first limit (100 m/s) was a guess. Cassini at the Earth has 155 m/s, which is 1.0 % of 16 km/s. 3 % is the documented accuracy of the zero-sphere-of-influence model. The numerical model then makes each flyby ballistic. |
| D17 | Real missions are made again from the sequence of bodies and the real dates only. The path is solved by the engine at run time. | The specification forbids trajectories that are made in advance. The dates are facts (JPL Horizons and NASA pages); the path is a result. |
| D18 | Conversion of a plan to a flight (`refinePlan`) has three stages. Stage A solves one control (launch velocity, correction maneuver or deep-space maneuver) for the aim point and the periapsis time of the next body. The aim point is measured on the approach hyperbola, about 30 body radii before the periapsis. Stage B makes each flyby ballistic: it changes the control before the flyby and the arrival velocity at the next body so that the correction after the flyby is a minimum (Gauss-Newton with equality constraints; the arrival time is fixed). Stage C (legs with a deep-space maneuver) moves the aim point of the flyby before the maneuver with a simplex search. | The osculating hyperbola at the periapsis of an oblate planet is not the approach asymptote (Jupiter: 2 % in the speed at infinity). The dates of a good plan are near the minimum of the energy, where the speed does not change with the date: an arrival-time unknown makes the Jacobian singular. |
| D19 | A plan can correct the flyby times for the time that the spacecraft is inside the sphere of influence (`soiTime`). | The zero-sphere patched-conic model puts the flyby at the wrong time by hours for Jupiter. The correction gives a better first estimate to the numerical solver. |
| D20 | An encounter report has two speeds at infinity: `vinf` (approach hyperbola) and `vinfClosest` (two-body orbit of the state at the closest approach, GM of the planet system). | The truth values from JPL Horizons use the second definition. A comparison must use the same definition (Pioneer 11 at Jupiter: 2 % difference between the two). |
| D21 | Real missions from their dates: limit of the periapsis radius of a flyby 3 %, speed at infinity 1 %, sum of the correction maneuvers 200 m/s. | The reproduction knows only the dates. The real flights used maneuvers that it does not know: the velocity jumps in the JPL Horizons trajectory of Cassini between Venus 2 and the Earth sum to 97 m/s (measured in `tests/famous.test.ts`). |
| D22 | The integrator ends each step at a time that a 64-bit number can hold, gives the stage times to the force model as start + offset, and uses compensated sums for the state. The ephemeris reader has a two-part time argument. Default relative tolerance 1e-13. | Measured 2026-10-14: the end position of a flight of 0.8 years from a parking orbit had a noise of about 1 km. The cause was the rounding of the time (1.2e-7 s near 2030 = 2 mm of motion for each step, multiplied by 7e4 by the escape from the Earth), not the tolerance. After the change the noise is 0.003 km, and 352 of 352 default missions are solved (before: 334). |
| D23 | A maneuver that a solver computed has an `anchor`: the state immediately after the impulse. The propagation continues from the anchor if its own state is nearer than 1 km and 1 mm/s; the difference is in the maneuver event. | A path with three flybys multiplies a difference in the last bit of a number to thousands of kilometres, and JavaScript engines do not round all functions equally. With anchors, a saved mission gives the same trajectory in all browsers. Each arc is still an integration of the engine. An edit of a maneuver must remove the anchors after it. |
| D24 | Quick mission (Explorer mode): the user gives a target, a goal (flyby, orbit, rendezvous, entry) and a style (efficient, fast). The engine searches launch dates for one synodic period (1.1 to 3 years) and flight times from 0.35 to 1.7 Hohmann times (not more than 16 years) on a 96 x 120 grid, then on a fine grid. Efficient = minimum velocity change. Fast = shortest flight for not more than 1.0 km/s (flyby, entry) or 1.5 km/s (orbit, rendezvous) above the minimum. Default altitudes are in `QUICK_ALTITUDE`. The orbit at Pluto is inside the orbit of Charon. | One minute from the first screen to a flight. The same solver and force model as the Expert mode. An orbit that crosses the orbit of Charon is chaotic. |
| D25 | The arrival burn is one impulse at the periapsis. Its size is solved so that the first apoapsis of the propagated orbit has the planned radius. Published values of real insertion burns (Cassini, Juno) are not used as truth. | Real insertion burns are long (Cassini: 96 minutes): the published velocity change includes gravity losses and is not the impulsive value. The comparison is in the list of items that are not verified. |
| D26 | The engine has no text for the user. Errors are codes (`QuickError.code`, `Trajectory.failure.reason`, `IoError.code`). The user interface translates the codes. | All text must be in the locale files (D12). |
| D27 | The spacecraft are original procedural models (nine models in `src/render/spacecraft`). They have no logo, no flag and no text. Main dimensions follow public documents where `docs/ASSETS.md` says so. | No licence question, no download, and the models are small. A box with panels is not acceptable. |
| D28 | Body maps are real mission data only, with a licence statement that can be quoted. Files from Solar System Scope are not used. The Sun, the cloud top of Venus and bodies with no map are drawn by shader code, and the product says that these are not photographs. | The first texture set had nine files from Solar System Scope (CC BY 4.0). They are assets of an existing application and contain invented fill. The specification forbids imitation of the assets of existing software and asks for a real look. |
| D29 | `tests/quick.test.ts` (352 default missions) and the last-encounter checks are tests of the solvers: the target is an input. They are not a validation of the physics. | The specification forbids tests that use the output of the code as truth. These tests are named as solver tests, and the validation report keeps them in a separate group (`solver`). |
| D30 | All long calculations run in a Web Worker (`src/app/worker.ts`). If the browser cannot start a worker, the same code runs on the page. | The user interface must not stop during a calculation of 10 seconds. A static host needs no special headers for this. |
| D31 | Each number on a screen has a basis: a `kind` that gives the method, the limit and the evidence (`src/app/provenance.ts`). The tests write each measured value to `src/validation/measured/*.json`, and the Accuracy screen shows these files. | The specification requires that the user can see the accuracy limit and the basis of each number. A value that a person copies into the text becomes wrong when the code changes. |
| D32 | The text of each language is a directory (`src/i18n/locales/en/`) with some JSON files that the application merges. (This replaces the single file of D12.) | One file of 100 kB is hard to maintain. A new language is still a new directory with no change to the code. |
| D33 | A trajectory table that the application writes has the steps of the integrator as its samples (default). Before it writes a file, the application measures the interpolation error of the table with the interpolation of the target program and shows it. The STK file asks for Hermite interpolation with 4 points, the same as the check. Limits: 100 000 samples in a written file, 64 MB for a file that the application reads. | Measured: a table of Voyager 2 with a fixed step of 1 day has an interpolation error of 149 038 km at Neptune. The table with 1569 integrator steps has 0.058 km. A fixed step is the usual default of other programs, and its error is not visible to their users. |
| D34 | Closest approaches of a table from a file: the application finds each interval in which the range rate to a body goes from negative to positive, then propagates the sample at the start of the interval to the sample at its end. It shows the distance between the end of this propagation and the sample of the file (`missKm`) and gives a warning above 1000 km. | A minimum of the sample distances does not find a flyby between two samples. Measured with a table of Cassini that has one sample each 10 days relative to the Sun: all four flybys before Saturn are found, and the three low flybys agree with the 1-minute data within 3.71 km and 0.16 s. A large `missKm` shows a maneuver in the interval (Saturn orbit insertion: 144 327 km). |
| D35 | A flight that the application makes from a table has one start state (a sample of the table) and the maneuvers that the user selects. The path is propagated by the engine, not copied from the table. The difference between the flight and the table is a graph. Maneuvers that the search finds in an interval with a flyby are not selected at the start. | The specification forbids a path that is not a result of the engine. The user sees how far a ballistic model is from the file, and can use the targeter to remove the difference. A maneuver estimate in a flyby interval is sensitive to small errors. |
| D36 | For a JPL Horizons table of a spacecraft relative to the solar system barycenter, the Files screen shows a caution. | Measured: such tables disagree with the tables relative to a planet by 118 km (Cassini, 1999) and 117 km (Juno, 2013). The altitude of the Earth flyby of Cassini from the barycenter table is 86 km too small. The cause is not verified. |
| D37 | A GMAT script that the application writes has the list of the differences between the two force models as comments. The Files screen says that the read of the files by GMAT and by STK is not verified. | GMAT and STK are not available in this work. A file that looks compatible but was not tested must say so. |
| D38 | The comparison flights of the Propagation screen (one force removed or added) start again at each maneuver from the state of the flight on the screen (default). An option gives one start only. | With one start, each flyby multiplies a small difference, and the values after two flybys only show that the flight is sensitive. With a start at each maneuver, a value shows the effect of the force in one arc. |
| D39 | The maps of Deimos, Miranda, Ariel, Umbriel, Titania and Oberon are the Caltech/JPL/USGS maps from Viking and Voyager images (public domain, from NASA 3D Resources and Wikimedia Commons). The areas of these maps with no image data stay as they are: the renderer shows them as flat dark grey and the product says so. | These maps are government data products, not the look of a commercial product, and USGS Astrogeology has no other mosaic of these bodies. A sphere with one color is not acceptable, and an invented surface is false. |
| D40 | Saturn, Uranus and Neptune use the global maps of the Hubble OPAL program (CC BY 4.0). The build fills the latitudes that the telescope cannot see with the mean color of the nearest rows, and the asset list says where. | No spacecraft made a global color map of these planets with a clear license. The fill is a small, declared part of each map. |
